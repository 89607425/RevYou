## 一、项目背景与问题定义

### 1.1 行业现状

在企业研发协作过程中，PRD评审是需求从"设计"走向"实现"的关键质量卡口。然而，当前评审流程存在以下系统性问题：

| 问题类别 | 具体表现 | 业务影响 |
|----------|---------|---------|
| 需求质量 | PRD描述不完整，遗漏边界条件、异常流、状态流转 | 评审返工率高，开发阶段频繁补需求 |
| 测试覆盖 | 测试场景覆盖不足，边界Case和异常流依赖人工补充 | 线上缺陷逃逸率高 |
| 技术风险 | 技术可行性风险未提前暴露 | 开发中期方案推翻，工期延误 |
| 历史冲突 | PRD与历史需求/已有逻辑冲突但未被识别 | 线上回归Bug |
| 知识沉淀 | 评审问题缺乏结构化沉淀，经验无法复用 | 同类问题反复出现 |
| 流程割裂 | 评审后仍需人工创建TAPD任务 | 信息丢失、流程断裂 |

### 1.2 根因分析

当前评审流程高度依赖三个"人力卡口"：

- **产品经理经验**：新人PM容易遗漏，资深PM也有盲区
- **开发主动发现问题**：依赖开发对需求的审慎程度
- **测试人工补充Case**：边界条件覆盖不全

这三个卡口导致：

| 结果指标 | 当前痛点 |
|----------|---------|
| 评审返工率 | 高（缺乏预检，问题在评审会上集中爆发） |
| 沟通成本 | 高（评审会冗长，反复拉通） |
| 工单遗漏率 | 高（评审问题口头提出，未系统记录） |
| 需求推进效率 | 低（从PRD完成到开发启动周期长） |

### 1.3 解决方案定位

构建一个**接入企业研发协作平台（TAPD）的AI需求评审Agent系统**，在正式评审前自动完成：需求预审 → 风险识别 → 问题沉淀。

**核心假设**（需在MVP阶段验证）：

1. AI多角色审查能有效发现PRD中的逻辑漏洞和遗漏（有效问题召回率 ≥ 60%）
2. 预审机制能显著降低评审返工次数（目标降低 ≥ 40%）
3. 自主Agent模式（追问、追加审查）能进一步提升复杂需求的审查深度

## 二、产品定位

### 2.1 一句话定义

**面向企业研发团队的AI需求评审与协作Agent平台**——在PRD进入正式评审前，通过多角色Agent自动进行需求走查、问题发现、结构化分析，并支持自主追问与追加审查，实现风险提前暴露、评审效率提升、需求资产沉淀。

### 2.2 核心价值主张

| 对谁 | 痛点 | 价值 |
|------|------|------|
| 产品经理 | PRD评审返工多、漏洞靠人肉发现 | AI预审自动发现问题，降低返工率 |
| 开发负责人 | 技术风险评审时才暴露 | 提前识别技术不可行点、数据一致性问题 |
| 测试人员 | 边界Case靠经验补充 | 自动生成边界测试Case和异常流Case |
| 项目经理 | 需求风险缺乏全局视图 | 统一查看风险等级、未解决问题、阻塞项 |

### 2.3 非目标（Non-goals）

> 明确本产品**不做**什么，防止范围蔓延：

1. ❌ 不替代人工评审决策——AI是辅助工具，最终判断权在人
2. ❌ 不自动修复代码或自动改写PRD——仅提供问题识别和建议
3. ❌ 不构建企业级知识库RAG——MVP阶段不做长期记忆与知识检索
4. ❌ 不做需求生成——本产品聚焦"评审"，不覆盖"编写"
5. ❌ 不做项目管理/排期功能——项目管理仍由TAPD原生功能承担
6. ❌ 不做代码审查——仅聚焦PRD/需求层面
7. ❌ 不集成飞书——本产品不与飞书平台对接（文档导入、通知、组织同步均不涉及）

## 四、核心业务流程

### 4.1 端到端流程

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  Step 1      │    │  Step 2      │    │  Step 3      │    │  Step 4      │    │  Step 5      │
│  导入需求    │───▶│  Agent预审    │───▶│  问题结构化   │───▶│  人工确认     │───▶│  结果导出    │
│              │    │  (多角色)     │    │  输出         │    │  & 处理       │    │              │
└─────────────┘    └──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
       │                   │                   │                   │                   │
       ▼                   ▼                   ▼                   ▼                   ▼
  PRD解析/结构化     PM/Dev/QA Agent     问题表+风险面板     标记误报/手动关闭    导出审查报告
  图片内容识别       并行审查            置信度标注          补充信息/重新审查    用户自行同步TAPD
  模块识别           自主追问(可选)                                              
```

### 4.2 Step 1：导入需求

#### 支持的导入方式

| 方式 | 支持格式 | 说明 |
|------|---------|------|
| 粘贴文本 | 纯文本/Markdown | 最大长度：50,000字符 |
| 上传文件 | PDF、Word(.docx)、图片（PNG/JPG/JPEG） | 单文件最大：20MB；图片用于辅助审查 |
| TAPD需求单导入 | TAPD Story ID / URL | 通过TAPD OpenAPI拉取需求详情（含附件图片） |

#### TAPD需求单导入详细说明

通过TAPD OpenAPI拉取需求单时，系统获取以下内容：

| 获取内容 | API | 说明 |
|----------|-----|------|
| 需求标题与描述 | GET /stories | 拉取Story详情 |
| 需求附件（图片） | GET /stories/{id}/attachments | 拉取附件列表及图片文件 |
| 需求评论 | GET /stories/{id}/comments | 拉取历史讨论内容 |
| 关联缺陷 | GET /stories/{id}/bugs | 拉取关联的已知缺陷 |

> **图片识别**：TAPD需求中的附件图片（流程图、原型图、架构图等）将通过多模态AI模型进行内容识别，提取文字与图形信息后纳入审查范围。

#### 系统自动处理

1. **结构提取**：识别标题、章节、列表、表格等文档结构
2. **模块识别**：按功能模块拆分PRD内容（如：用户流程、数据模型、接口定义等）
3. **元数据提取**：提取需求ID、需求名称、所属项目等关键信息
4. **图片内容识别**：对上传的图片和TAPD附件图片，通过多模态模型提取文字、流程、架构等信息，合并入审查内容

#### 异常处理

| 异常场景 | 处理方式 |
|----------|---------|
| 文件格式不支持 | 提示"暂不支持该格式，请使用PDF/Word/纯文本/图片" |
| 文件大小超限 | 提示"文件超过20MB限制，请精简后重试" |
| 文本长度超限 | 提示"内容超过50,000字符限制，建议拆分后分次审查" |
| PRD解析失败（无法识别结构） | 以全文作为审查对象，提示"未识别到标准PRD结构，将按全文模式审查" |
| TAPD需求单不存在/无权限 | 提示"需求单不存在或无权限访问，请检查ID和TAPD令牌配置" |
| 图片识别失败 | 跳过该图片，提示"图片'{filename}'识别失败，已跳过，建议以文字补充描述" |
| 导入内容为空 | 提示"未检测到有效内容，请检查输入" |

### 4.3 Step 2：Agent多角色预审

系统启动多个角色Agent**并行审查**（非串行），每个Agent独立输出审查结果。

#### PM Review Agent

| 关注维度 | 审查项 |
|----------|--------|
| 用户流程完整性 | 主流程是否有明确起点和终点；分支流程是否覆盖所有决策节点 |
| 状态流转 | 状态机是否定义完整；是否存在不可达状态或无法退出的状态 |
| 埋点缺失 | 关键用户行为是否有埋点定义；漏斗关键步骤是否有数据采集方案 |
| 文案一致性 | 同一概念在不同章节的用词是否一致；UI文案与功能描述是否匹配 |
| 边界条件 | 数值边界（最大/最小值）是否定义；空值/默认值是否说明 |
| 异常流 | 操作失败后的处理是否定义；超时/网络异常是否覆盖 |

#### Dev Review Agent

| 关注维度 | 审查项 |
|----------|--------|
| 技术风险 | 是否存在当前技术栈无法实现的功能；是否有未评估的第三方依赖 |
| 接口依赖 | 接口契约是否定义（入参/出参/错误码）；上下游接口是否对齐 |
| 数据一致性 | 跨表/跨服务的数据更新是否有事务保障方案；缓存与DB一致性是否考虑 |
| 幂等问题 | 重复提交场景是否有幂等设计；支付/库存等关键操作是否防重 |
| 并发问题 | 高并发场景是否有限流/队列方案；竞态条件是否考虑 |
| 兼容性 | 是否涉及老版本兼容；数据迁移方案是否说明 |

#### QA Review Agent

| 关注维度 | 审查项 |
|----------|--------|
| 边界条件 | 数值边界测试Case是否可推导；输入格式边界是否覆盖 |
| 异常流程 | 操作失败路径是否有测试覆盖；异常数据输入是否考虑 |
| Case遗漏 | 状态流转全路径是否可生成Case；权限边界是否覆盖 |
| 状态覆盖 | 所有状态转换是否有对应测试场景；状态回退是否考虑 |

#### Data Review Agent（Phase 2，MVP不实现）

> MVP阶段不做Data Review Agent。Phase 2根据MVP数据决定是否启用。

| 关注维度 | 审查项 |
|----------|--------|
| 数据埋点 | 埋点方案是否与业务指标对齐 |
| 指标缺失 | 核心业务漏斗是否有对应指标定义 |
| 漏斗分析 | 是否具备漏斗归因分析的数据基础 |

#### Agent执行约束

| 约束项 | 确定性工作流配置值 | 自主Agent模式配置值 | 说明 |
|--------|-------------------|--------------------|------|
| 单Agent最大审查轮次 | 1轮 | 3轮 | 自主模式允许追加审查 |
| 单Agent最大输出问题数 | 30条 | 30条 | 防止输出爆炸 |
| 全部Agent并行超时 | 5分钟 | 10分钟 | 自主模式需更多时间 |
| 单文档最大Token数 | 32K tokens | 32K tokens | 超长文档截断或分片处理 |
| 最大自主追问次数 | 0次 | 5次 | 仅自主模式生效 |
| 联网搜索 | 不允许 | 允许（需标注来源） | 仅自主模式生效 |

### 4.4 Step 3：问题结构化输出

#### 问题数据模型

```json
{
  "issue_id": "ISS-20260611-001",
  "review_session_id": "RS-20260611-001",
  "source_agent": "PM_REVIEW | DEV_REVIEW | QA_REVIEW",
  "issue_type": "TECHNICAL_RISK | LOGIC_GAP | TEST_MISSING | DATA_INCONSISTENCY",
  "severity": "HIGH | MEDIUM | LOW",
  "title": "问题标题（简明一句话）",
  "description": "问题详细描述",
  "suggestion": "Agent建议的解决方案",
  "prd_section": "对应PRD章节（如：三、核心业务流程 > 4.2 Step 2）",
  "image_ref": "引用的图片来源（如：TAPD附件'storage_flow.png'）",
  "confidence": 0.85,
  "status": "OPEN | CONFIRMED | FALSE_POSITIVE | RESOLVED | DEFERRED",
  "created_at": "2026-06-11T10:00:00Z",
  "updated_at": "2026-06-11T10:00:00Z",
  "resolved_by": null,
  "resolution_note": null
}
```

#### 严重等级定义

| 等级 | 定义 | 示例 |
|------|------|------|
| HIGH | 逻辑矛盾/技术不可行/可能导致线上事故 | "支付流程缺少幂等设计，可能导致重复扣款" |
| MEDIUM | 信息缺失/边界未定义/可能导致返工 | "状态流转未定义'退款中'状态的退回路径" |
| LOW | 文案不一致/格式问题/建议优化 | "章节2和章节5对同一功能使用了不同命名" |

#### 置信度定义与阈值

| 置信度区间 | 标识 | 处理方式 |
|-----------|------|---------|
| 0.8 - 1.0 | 高置信度 | 正常展示，标记为 ✅ 高可信 |
| 0.5 - 0.8 | 中置信度 | 正常展示，标记为 ⚠️ 需人工确认 |
| 0.0 - 0.5 | 低置信度 | 折叠展示，标记为 ❓ 低置信度，默认不纳入导出报告 |

> 置信度阈值（0.5/0.8）为初始值，上线后根据误报率数据调优。

#### 输出形式

| 形式 | 说明 | 适用场景 |
|------|------|---------|
| 问题表格 | 按Agent/严重等级排列的完整问题列表 | 详细查看每个问题 |
| 风险面板 | 仪表盘式展示：风险等级分布、未解决问题数、阻塞项 | 项目经理全局概览 |
| 评论流 | 以PRD章节为锚点的inline评论 | PM逐章节定位问题 |

### 4.5 Step 4：人工确认与处理

#### 用户操作

| 操作 | 说明 | 权限 |
|------|------|------|
| 确认问题 | 标记问题为"已确认"，进入待处理状态 | PM / Dev / QA |
| 标记误报 | 标记问题为"误报"，需填写误报原因（必填） | PM |
| 手动关闭 | 直接关闭问题，填写关闭原因 | PM / 管理员 |
| 重新审查 | 指定某个Agent对特定章节重新审查 | PM |
| 回复问题 | 补充信息或给出解决方案 | Dev / QA |
| 提升严重等级 | 将问题从中/低提升为更高等级 | PM / 管理员 |
| 降低严重等级 | 将问题从高/中降低等级，需填写原因 | PM |

#### PRD修改后的审查策略

| 场景 | 策略 |
|------|------|
| PRD仅修改个别章节 | **增量审查**：仅对修改章节重新触发Agent审查，未修改章节保留原审查结果 |
| PRD大范围修改（修改章节 > 50%） | **全量重审**：重新触发全部Agent审查，原审查结果标记为"已过期"并归档 |
| 用户主动触发全量重审 | 提供手动"重新审查"按钮，无论修改范围均全量重审 |

### 4.6 Step 5：结果导出

> ⚠️ **重要约束**：MVP阶段本平台对TAPD仅拥有**只读权限**（通过TAPD API Token访问），不具备向TAPD创建/修改工单的权限。因此，审查结果不自动同步至TAPD，而是由用户自行操作。

#### 导出方式

| 方式 | 格式 | 说明 |
|------|------|------|
| 审查报告导出 | Markdown / PDF | 包含完整问题列表、严重等级、建议方案 |
| 问题清单导出 | Excel / CSV | 结构化数据，便于用户手动在TAPD中批量创建工单时参考 |
| 一键复制（单条问题） | 剪贴板 | 复制问题标题+描述+建议，格式适配TAPD工单字段，方便粘贴 |

> **后续规划**：Phase 2根据MVP使用数据评估是否申请TAPD写权限，实现工单自动创建与双向同步（详见第六章）。

## 五、Agent工作模式

### 5.1 模式一：确定性工作流

```
PRD解析 → 多角色并行审查 → 问题汇总分类 → 人工确认 → 结果导出
```

| 特点 | 说明 |
|------|------|
| 稳定 | 流程固定，每一步可预期 |
| 可控 | Agent不自主追问，不自主追加审查 |
| 输出一致 | 相同输入产生可比的输出结构 |
| 可追溯 | 每个问题的产出Agent和审查轮次可追溯 |
| 速度快 | 单轮审查，5分钟内完成 |

**适用场景**：需求描述清晰、功能模块明确的标准PRD审查。

### 5.2 模式二：自主Agent模式

```
PRD解析 → 多角色并行审查 → 自主追问/追加审查 → 问题汇总分类 → 人工确认 → 结果导出
                              ↑___________↓
                          （Agent可发起追问，用户确认后继续）
```

允许Agent在审查过程中：

| 能力 | 说明 | 约束 |
|------|------|------|
| 主动追问 | Agent发现信息缺失时，向用户发起追问（如："PRD中未说明用户未登录时的行为，请补充"） | 单次审查最大追问次数：5次；追问需用户确认后才发送 |
| 自动追加审查轮次 | 发现新线索后，Agent可自主进行第二轮审查 | 最大追加审查轮次：2轮（共3轮）；轮次间需等待用户确认 |
| 联网搜索竞品方案 | 搜索行业最佳实践进行对比分析 | 搜索结果必须标注来源URL |
| 自动关联TAPD历史缺陷 | 读取当前项目TAPD中的历史缺陷，关联同类问题 | 仅读取，不写入；需TAPD API Token配置 |

**自主追问交互流程**：

```
Agent发现信息缺失
    ↓
生成追问内容（如："第3章'支付流程'未定义支付超时后的处理逻辑，请补充"）
    ↓
用户收到追问通知（站内信 / 页面内弹窗）
    ↓
用户选择：
  A. 补充信息 → Agent继续审查
  B. 跳过追问 → Agent标记该点为"信息不足"，继续审查其余部分
  C. 终止追问模式 → 切换回确定性工作流，返回已有结果
```

**适用场景**：复杂需求评审、需求描述存在明显缺失或歧义的情况。

### 5.3 模式选择规则

| 条件 | 默认模式 | 用户可手动切换 |
|------|---------|---------------|
| 首次提交审查 | 确定性工作流 | 是，可主动选择自主Agent模式 |
| 确定性工作流发现 > 5个HIGH问题 | 自动提示"建议切换至自主Agent模式进行深度审查" | 用户可选择切换或保持 |
| 用户手动选择自主Agent模式 | 自主Agent模式 | 是，可在审查开始前切换 |
| 自主模式追问达到上限 | 自动降级为确定性工作流 | 不可逆 |

### 6.2 Phase 2规划：TAPD写集成（MVP不实现）

> ⚠️ 以下为未来规划，需在Phase 2根据MVP使用数据评估是否申请TAPD写权限后实施。

#### 自动创建TAPD任务

**触发条件**：满足以下全部条件时，支持"一键生成TAPD缺陷/任务单"：

1. 问题严重等级 = HIGH，且置信度 ≥ 0.8
2. 用户已确认该问题（status = CONFIRMED）
3. 用户点击"创建TAPD工单"按钮
4. 平台已获取TAPD项目写权限

**自动填充字段**：

| TAPD字段 | 填充来源 | 说明 |
|----------|---------|------|
| 标题 | issue.title | 格式：【AI审查】{title} |
| 问题描述 | issue.description + issue.suggestion | 合并问题详情和建议方案 |
| 优先级 | 映射：HIGH→紧急，MEDIUM→高，LOW→中 | |
| 关联需求 | review_session关联的TAPD Story ID | 导入时自动关联 |
| 指派人 | 默认指派给需求Owner（从TAPD需求单获取） | 用户可修改 |
| 自定义标签 | ai-review | 便于后续筛选AI生成的工单 |

#### 工单状态双向同步

| 方向 | 触发 | 同步内容 | 冲突处理 |
|------|------|---------|---------|
| AI → TAPD | 用户确认问题并创建工单 | 问题状态、描述、建议方案 | AI侧为准 |
| TAPD → AI | 定时轮询（5分钟间隔）/ Webhook回调 | 工单状态变更、处理人变更、最新评论 | TAPD侧为准 |

**冲突处理原则**：

- **状态冲突**：以TAPD工单状态为准（TAPD是研发流程的Source of Truth）
- **描述冲突**：不自动覆盖，标记为"内容有差异"，提示用户手动对齐
- **处理人冲突**：以TAPD当前处理人为准

### 6.3 历史需求学习（Phase 2，MVP不实现）

> ⚠️ 本节为未来规划，MVP阶段不实现。

**Phase 2目标**：读取历史TAPD问题单，自动学习高频Bug类型、常见需求遗漏、历史事故模式。

**示例**："库存类需求过去3个月有较多超卖问题，请重点检查幂等逻辑。"

**Phase 2需额外定义**：

- 历史数据范围（最近N个月/N条）
- 学习频率（每周全量/增量）
- 学习结果如何注入Agent审查逻辑
- 数据脱敏与隐私合规

## 八、异常与兜底机制

### 8.1 幻觉控制

| 机制 | 说明 |
|------|------|
| 低置信度标识 | 置信度 < 0.5 的问题折叠展示，不纳入导出报告 |
| 引用溯源 | 每个问题的描述必须引用PRD原文片段或图片来源，不可凭空捏造 |
| 人工校准入口 | 用户可标记误报，误报数据回流用于模型优化 |
| 输出后处理 | Agent输出经过规则引擎过滤：去除与PRD内容无关的问题 |

### 8.2 Agent循环保护

| 保护项 | 确定性工作流 | 自主Agent模式 | 触达后行为 |
|--------|------------|--------------|-----------|
| 单Agent最大审查轮次 | 1轮 | 3轮 | 停止审查，返回已有结果 |
| 单Agent最大输出问题数 | 30条 | 30条 | 截断输出，提示"问题较多，建议拆分审查" |
| 全部Agent并行超时 | 5分钟 | 10分钟 | 返回已完成的结果，标记未完成Agent为"超时" |
| Agent调用模型最大Token | 32K tokens/次 | 32K tokens/次 | 超长内容分片处理 |
| 最大自主追问次数 | 不适用 | 5次 | 停止追问，按确定性模式返回结果 |
| 联网搜索超时 | 不适用 | 30秒/次 | 跳过搜索结果，基于已有信息继续审查 |

### 8.3 人工接管机制

| 操作 | 说明 |
|------|------|
| 手动关闭某问题 | 关闭后归档保留记录 |
| 强制标记误报 | 误报记录回流模型优化流程 |
| 指定Agent重新审查 | 可指定特定Agent对特定章节重新审查 |
| 终止整个审查会话 | 立即停止所有Agent，返回已有结果 |
| 自主模式降级 | 用户可随时将自主Agent模式降级为确定性工作流 |
| 跳过追问 | 在自主模式追问时选择跳过，Agent标记该点为"信息不足" |

### 8.4 服务降级方案

| 故障场景 | 降级策略 |
|----------|---------|
| AI模型不可用 | 提示"AI服务暂时不可用"，允许用户稍后重试 |
| 多模态模型不可用 | 降级为纯文本模型审查，提示"图片识别服务不可用，仅进行文本审查" |
| TAPD接口不可用 | 审查正常进行（基于已导入内容），TAPD导入功能不可用，提示用户改用粘贴/上传 |
| 联网搜索不可用（自主模式） | 跳过搜索步骤，基于已有信息继续审查 |

## 十五、核心指标体系

### 15.1 北极星指标

**有效问题召回率** = AI发现的有效问题数 / （AI发现的有效问题数 + 评审后人工补充的问题数）

> 目标：MVP阶段 ≥ 60%

### 15.2 驱动指标

| 指标 | 定义 | 基线 | MVP目标 | 数据来源 |
|------|------|------|---------|---------|
| 平均评审耗时 | 从PRD提交到审查完成的平均时间 | 待基线（上线后采集） | 降低40% | 审查会话时间戳 |
| PRD返工次数 | 单个PRD从提交到通过评审的迭代次数 | 待基线 | 降低30% | 审查会话计数 |
| Bug提前发现率 | AI预审发现的问题中，若未发现会导致线上Bug的比例 | 待基线 | 追踪观察 | 线上Bug关联分析 |
| 自主模式追问触发率 | 使用自主Agent模式的审查会话占比 | — | 追踪观察 | ReviewSession统计 |

### 15.3 健康指标

| 指标 | 定义 | 告警阈值 | 数据来源 |
|------|------|---------|---------|
| AI误报率 | 标记为"误报"的问题数 / 总问题数 | > 30% 告警 | ReviewIssue状态 |
| 日活用户(DAU) | 每日使用审查功能的独立用户数 | < 5 持续7天告警 | 用户行为日志 |
| 平均每份PRD审查问题数 | 所有审查会话的平均问题产出数 | > 50 告警（可能过度审查） | ReviewIssue统计 |
| 审查完成率 | 状态为COMPLETED的会话 / 总会话数 | < 90% 告警 | ReviewSession统计 |
| 图片识别覆盖率 | 成功识别的图片数 / 总图片数 | < 80% 告警 | 图片识别日志 |
| TAPD Token可用率 | Token验证成功的次数 / 总验证次数 | < 95% 告警 | Token验证日志 |

### 15.4 指标采集方式

- 前端埋点：用户操作行为（页面访问、按钮点击、操作耗时）
- 后端日志：审查会话生命周期、Agent执行日志、图片识别日志
- 定期统计：每日/每周自动生成指标报表

### 17.2 技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | Next.js | SSR + 组件化，企业级体验 |
| 后端 | FastAPI | 异步高性能，Python生态对AI友好 |
| Agent框架 | LangGraph | 支持多Agent编排、状态管理、流程控制、自主模式 |
| AI模型（文本） | DeepSeek-V3（默认） | 性价比最优的纯文本审查 |
| AI模型（多模态） | Qwen-VL-Max（默认）/ GPT-4o | 图片识别+文本审查，含图片时自动切换 |
| 主数据库 | PostgreSQL | 存储审查会话、问题等结构化数据 |
| 向量检索 | pgvector / Milvus | Phase 2：用于历史需求学习和知识库RAG |
| 企业集成 | TAPD OpenAPI（只读） | 通过API Token认证，拉取需求、附件、评论 |
| 部署 | Docker + K8s | 容器化部署，支持弹性扩缩容 |

### 17.3 关键技术决策

| 决策 | 选择 | 原因 |
|------|------|------|
| Agent并行 vs 串行 | 并行 | 降低审查耗时，各Agent独立无依赖 |
| 文档解析方案 | 开源库（PyPDF2/python-docx）+ 多模态模型 | 文本解析+图片识别双通道 |
| TAPD认证方式 | API Token | MVP仅需只读权限，Token方式最轻量；Phase 2视需评估OAuth |
| 增量审查实现 | 基于章节级Diff | 仅对变更章节触发Agent，减少Token消耗 |
| 模型路由策略 | 自动检测图片→切换多模态模型 | 对用户透明，无需手动选择 |
| 自主模式实现 | LangGraph的Human-in-the-loop | 追问需用户确认，符合LangGraph原生设计 |

## 十八、隐私合规

### 18.1 数据安全

| 要求 | 实现方式 |
|------|---------|
| PRD内容加密存储 | 数据库字段级加密（AES-256） |
| TAPD Token加密存储 | 单独加密，访问时解密，不落日志 |
| 传输加密 | 全链路HTTPS |
| 数据隔离 | 租户级数据隔离，跨项目不可见 |
| 数据保留 | 审查记录默认保留180天，超期自动清理 |
| 数据导出 | 管理员可导出本项目的全量审查数据 |

### 18.2 合规要求

| 法规 | 合规措施 |
|------|---------|
| 个人信息保护法 | 不采集用户个人身份信息；PRD内容中若包含个人信息，提示脱敏 |
| GDPR（如涉及海外） | 提供数据删除请求入口；明确数据处理者角色 |
| 企业数据安全 | TAPD接口调用遵循最小权限原则（MVP仅只读）；操作审计日志 |

### 18.3 AI模型数据安全

- PRD内容发送至AI模型前，**不**做额外脱敏（因PRD本身为内部文档）
- 优先使用私有化部署模型，避免数据出域
- 若使用云端模型，需确保模型供应商签署数据处理协议（DPA）
- 模型接口调用日志记录但**不**记录PRD原文内容
- TAPD附件图片仅用于审查时的多模态识别，审查完成后不保留原图（仅保留识别结果文本）

## 附录A：术语表

| 术语 | 定义 |
|------|------|

| 增量审查 | 仅对PRD修改部分触发审查，保留未修改部分的审查结果 |
| 全量审查 | 对整个PRD重新触发所有Agent审查 |
| TAPD API Token | TAPD平台提供的API访问令牌，用于程序化访问TAPD数据 |
